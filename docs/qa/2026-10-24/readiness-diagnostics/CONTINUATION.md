# Public readiness diagnostics continuation

Baseline: `21d4ff1cfcbe309b861fc87100ba0327d6479bb4` (the original-mode release). This continues the combined QA ledger without changing any strategy rules, mode, saved risk/control setting or broker order.

## Reproduced gaps and fixes

1. **An unsuccessful public readiness probe could return an empty reason.** The observed app and Telegram shells returned HTTP 200 and the private data route correctly returned 401, while public `/health` timed out. The original readiness function correctly refused publication but discarded transport/contract failures. Each failing probe now reports its route and a bounded diagnostic: for example `HEALTH_TIMEOUT`, `HEALTH_HTTP_503`, `APP_SHELL_INVALID`, `HEALTH_PAYLOAD_INVALID`, or `PRIVATE_API_AUTH_REQUIRED`. Exception text, provider pages and credentials are not echoed. Known ngrok quota codes remain recognized. All four probes remain concurrent, TLS verification remains enabled, and a successful private API response still prevents public readiness.
2. **Live status retained a stale external-supervisor recovery warning after health recovered.** The cached status contained `EXTERNAL_SUPERVISOR_RECOVERY_PENDING` while the current backend was healthy. A fresh status read now removes only that warning after confirming a listener and successful local health response. It does not rewrite cached state, clear other ownership warnings or infer health from an open port alone.

The existing presentation manager already holds an authenticated temporary tunnel. Its process is not restarted merely to load diagnostic code; that would discard the quick-tunnel origin. Updated CLI status/probe calls use the fixed code immediately after integration. The manager's periodic in-memory probe code will load it on its next normal restart. No restart, callback rotation or trading-control change is required for this patch.
